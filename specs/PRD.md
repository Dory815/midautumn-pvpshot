## 0. 项目背景与作者说明

作者是物理系本科生，对 Java 只有粗略了解，不熟悉前端。讨论与文档尽量使用中文，少用专业术语，必要的术语会就地解释。

做这件事的起因：现在这套枪战小游戏是用**数据包（datapack）**写出来的，功能已经能跑，但**优化太差**——服务器一忙起来就卡，加新玩法越来越费劲，改一处经常要连带改好几个生成脚本和覆盖层。

目标：用 **Minecraft Java 26.2 的 Fabric 服务端模组**把玩法重写一遍，把"卡"和"难维护"这两个根子上的问题解决掉，同时**尽量不要求玩家装客户端 Mod**。

### 0.1 一句话结论（先看这个）

**可以用纯服务端模组重构，而且这是本项目最合适的方向。**

- 玩法判定、伤害、计时、保护、地形恢复——**全部能放在服务端模组里**，玩家用原版客户端直接连就能玩。
- 只有"枪械模型动画、弹药 HUD 数字、后坐力/开镜手感、自定义音效事件"这类**纯观感与手感**的东西，才需要客户端 Mod；它们可以作为**可选增强**，装了更好，不装不影响公平和可玩性。
- 现在的项目其实已经在往 Java 走（有个 694 行的 Java 模块，靠"插桩"技术挂到官方服务端上），只是这条路走得比 Fabric 更别扭、更容易碎。换成 Fabric 是把这条路走正。

## 2. 现状介绍与实现功能

### 2.1 现在的系统由什么组成

```
玩家（原版客户端，HMCL 启动 26.2）
   │
   ▼
官方 Minecraft 26.2 服务端
   ├── 数据包 pvpshot      ← 通用玩法（大部分由 Python 脚本生成）
   ├── 数据包 ustc_pvp      ← 校园地图接线，并覆盖 pvpshot 的 3 个函数
   ├── Java 模块（插桩）    ← 精确判定：弓弩、连射、战斗机、重武器、设施保护
   └── 世界存档（含 ustc_pvp:template 私有维度，作为地形复原的"原件仓库"）
```

- 玩家**不需要装任何 Mod**，这是当前设计的重要优点，重构后要保留。
- 状态几乎全部存在**记分板（scoreboard）**、命令存储（command storage）、实体标签和物品组件里。
- 地图逻辑依赖完整存档里的 `ustc_pvp:template` 维度；单装地图数据包拿不到校园地形。

### 2.2 现在实际做到了什么

| 玩法 | 现状 |
|---|---|
| 模式 | 三点占领（目标 600）、五点占领（目标 1000）、团队死斗（目标 60），全员可切换 |
| 队伍 | 红/蓝队，出生点、队伍颜色、前线复活（30 个候选点，自动排除有敌人/悬空/头部堵塞） |
| 武器 | 火焰弹、破拆火箭、SMG、霰弹枪、弓弩、雪球、鸡蛋、三叉戟、手雷/温雷、轨道 380、飞鹰 500、空爆火箭筒、战斗机（限时 30 秒） |
| 投射物 | 三条实现路径：数据包自绘弹体、原生投射物+服务端规则、Java 直接射线 |
| 场景 | 炮与炮塔（右键部署）、大型掩体、80 个普通补给箱（60 秒补货）、2 个高级箱（300 秒，25% 出稀有装备） |
| 战场 | 科大中区实景地图，三点/五点共用东西基地，A/C 在楼顶 |
| 保护 | 181 个设施保护区域：大厅、基地、据点核心、箱子与开盖空间 |
| 复原 | 一键整场复原，覆盖 X=-2144…-1569、Z=-1776…-1153、Y=-16…127，从模板维度分 **176 批**复制回原样 |
| 手感 | 20 HP、友伤开启、饱食度常满、脱战 5 秒回血、命中标记发光 2 秒 |
| 质量 | 8 组官方引擎 GameTest，合计 1131 条 PASS 检查记录 |

### 2.3 为什么"优化太差"——用证据说话

这不是感觉问题，是可以指出具体位置的：

1. **每 tick 全员扫描。** `ustc_pvp:tick.mcfunction` 每 tick 执行 8 次 `as @a`（遍历所有玩家）+ 5 次 `scoreboard players enable @a`；`pvpshot:shot/tick.mcfunction` 每次弹体更新还要再来几次 `as @a`。命令式的"轮询"是数据包做实时玩法的通病：**你没法订阅事件，只能每 tick 挨个问一遍**。
2. **单个函数文件被撑到 137.9 KB。** `pvpshot/function/deploy/check_bunker.mcfunction`（大型掩体放置检查）是生成器暴力展开的产物。这类文件一次执行就是几千条命令，改起来也只能改生成脚本。
3. **弹体靠"小步走"模拟。** `shot/step.mcfunction` 每次只前进一小步（约 0.00002 格量级的速度换算），每步要算 7 条命令，还要用 `as @a[distance=..1.5]` 之类的方式找附近玩家，每 tick 循环 5 次（SMG 另有更快节奏）。命中判定用的是"逐步靠近 + 谓词"，不是真正的几何求交。
4. **每 tick 用 NBT 匹配筛实体。** `combat/proj_tick.mcfunction` 每 tick 对所有雪球/鸡蛋/箭执行 `nbt={Item:{components:{"minecraft:custom_data":{...}}}}` 匹配。NBT 匹配要先把实体数据序列化出来再比较，是命令系统里最贵的操作之一。
5. **地形恢复是命令堆出来的。** 176 个批次目录、每批一份 9.8 KB 的 `copy.mcfunction`，逐格 `clone`/`setblock`。恢复期间服务器基本在做"执行命令"这一件事。
6. **Java 模块的方式很脆弱。** 它用 Java 25 的插桩（Instrumentation）在类加载时改官方 `server.jar` 的字节码，并且**硬编码了官方 jar 的 SHA-1 校验值**。换个小版本、官方改个方法签名，就整套失效——`ProtectionAgent.transform` 里那句"Expected N hooks, found M"就是为了让它在不匹配时直接崩掉而不是悄悄半坏。它承担的功能却越来越重（已经不只是"protection"）。
7. **配置与生成链是覆盖式的。** 有"基础生成器 → v7 → v8"的覆盖顺序，单独重跑旧脚本会退回旧数值。同一份逻辑分散在脚本、数据包函数、Java 常量三处，容易出现"改了 A 忘了 B"。

补充说明：**这些不是作者写得差，而是数据包这套工具的固有天花板**。用命令语言做实时射击游戏，等价于用 SHELL 脚本写游戏引擎——能写出来已经说明作者很拼了。

### 2.4 线上运行情况（2026-09-23 快照）

| 项目 | 值 |
|---|---|
| 入口 | `<服务器IP>:28898`（LyerSkin 认证，authlib-injector 1.2.8） |
| 系统 / Java | Ubuntu 24.04.4 / OpenJDK 25.0.4.1 |
| 堆内存 | `-Xms512M -Xmx3G` |

## 3. 重构目标

### 3.1 必须达成

1. **性能**：12 人激烈交火（含霰弹枪、空爆、TNT、战斗机）时，服务端 tick 时间稳定在目标值的 50% 以内，不出现持续掉 tick。
2. **不卡顿的复原**：整场地形复原期间服务器保持可响应，玩家在大厅能看到进度；复原过程中不再长时间"卡住不动"。
3. **玩家零安装**：玩家用原版 26.2 客户端（经 HMCL + LyerSkin 登录）能加入并完整体验，不需要装任何 Mod 或资源包。
4. **玩法不缩水**：2.2 表格里的功能**全部保留**，且手感不劣化（伤害、冷却、射速、判定按《武器平衡表.md》为准）。
5. **可维护**：武器数值、地图点位、保护区域、补给规则各有**唯一一份**数据来源，改一处就生效，不再有"生成器覆盖顺序"。
6. **开局干净**：世界存档（玩家、地形、点位标记）能直接沿用，玩家不用重新盖地图。

### 3.2 明确不做（本期范围外）

- 不换玩法的核心规则（模式、计分、目标分数、复活规则保持 2.2 的描述）。
- 不做公开服的一键部署/自动更新系统（沿用现有 SSH + tmux 流程，后续再单独提需求）。
- 不重做地图美术、不新增武器（除非另开需求条目）。
- 不做反作弊系统（服务端权威已能挡住大部分改数值类作弊）。
- 不迁移 `before/` 里的历史日志、发布包、世界快照到 git（见 3.4）。

### 3.3 客户端策略（本项目的关键决策）

分三档，**第一档是必须做到的底线**：

| 档位 | 玩家需要装什么 | 得到什么 |
|---|---|---|
| A（底线，必须有） | 什么都不装，原版客户端 | 完整玩法、伤害、判定、计分、UI（原版可见的提示/血条/Bossbar/物品外观） |
| B（可选，服务器资源包） | 什么都不装，接受服务器下发的资源包 | 枪械模型与贴图、UI 贴图（准星等）、替换过的音效——**仍然不需要 Mod** |
| C（可选，客户端 Mod） | 装一个 Fabric 客户端 Mod | 弹药 HUD 数字、命中反馈、伤害数字、后坐力/开镜动画、自定义按键、更精细的声音定位 |

规则：**A 档必须是完整的**；B、C 只能"更好看、更好用"，绝不能出现"不装就吃亏"（比如 C 档能看到别人看不到的信息）。

### 3.4 版本控制策略

- 在 `MidAutumnMiniGame/` 建立 git 仓库，**每次改动都要提交**，提交信息用中文写清改了什么。
- `before/` 的**文本源码**（`.mcfunction`、`.json`、`.java`、`.py`、`.md`、地图方案 JSON 等，约 1000 个文件 / 4 MB）纳入 git，方便对照。
- **不纳入 git**：`.zip`、`.mca`、`server.jar`、`发布/`、`测试存档/`、`__MACOSX/`、`__pycache__/`、`.DS_Store` 等二进制与分发产物（合计约 2.5 GB，进 git 会让仓库变得不可用）。理由与规则见 `.gitignore` 内注释。

## 4. 效果描述

### 4.1 玩家视角（重构前后对比）

| 场景 | 现在 | 重构后 |
|---|---|---|
| 加入游戏 | 原版客户端直连 | **不变** |
| 开枪手感 | 弹体是数据包画的小实体，高速时有"跳格"风险（靠小步扫描补救） | 服务端几何射线判定，命中准确；弹道用粒子表现，视觉连续 |
| 多人交火 | 人越多、弹越多越卡 | 计算量与人数线性相关，弹体只算"有没有打中" |
| 整场复原 | 逐格命令恢复，过程较长 | 直接写地形数据，秒级完成；期间服务器保持流畅 |
| 大厅操作 | 原版容器/GUI 按钮 | 不变或更顺手（原版对话框） |
| 视觉 | 武器是原版物品（火焰弹=火焰弹物品之类） | 可选资源包提供枪械模型；不装资源包则是原版物品外观，功能一致 |

### 4.2 管理员视角

- 上线/更新流程不变（替换 jar 与配置、`manage.sh` 控制），但**不再需要给官方服务端打字节码补丁**，也不用维护 jar 的 SHA-1 校验。
- 新增：结构化的状态查询（一局进行到哪、谁在哪个点、弹体/部署物有多少），不必再靠读记分板猜。
- 配置集中在少量 JSON/常量里，改武器数值不用重跑一长串生成脚本。

### 4.3 开发者视角

- 逻辑集中在 Java，能在 IDE 里断点调试、能写单元测试。
- 武器/点位/保护区域各有唯一定义处，"改一处生效"。
- 不再有 137 KB 的单个函数文件、不再有 v7/v8 覆盖顺序。

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 12 人满载荷交战时 tick 时间 ≤ 25 ms（20 tps 的 50%）；复原期间单 tick 额外开销 ≤ 5 ms |
| 兼容 | Minecraft Java 26.2；玩家端零安装；LyerSkin 认证照旧可用 |
| 存档 | 直接使用现有世界（含 `ustc_pvp:template` 维度、点位 marker、保护区域） |
| 可维护 | 单一数据来源；无生成器覆盖顺序；新增武器只需改 1~2 处 |
| 可观测 | 关键状态可查询；异常有明确日志，不静默降级 |
| 安全 | 服务端权威；不因客户端未安装 Mod 而拒绝服务；自定义网络包必须确认对方能收 |
| 部署 | 沿用现有服务器目录结构与 `manage.sh`；不改变玩家连接方式 |

## 9. 术语对照（给非专业读者）

| 术语 | 通俗解释 |
|---|---|
| 数据包（datapack） | 用游戏内的"命令脚本"实现玩法，不改程序本体 |
| 模组（mod） | 真正修改/扩展游戏程序代码，能直接做复杂计算 |
| 服务端模组 | 只装在服务器上；玩家端不需要装 |
| Fabric | 一个轻量的 Minecraft 模组加载器，支持只装服务端的模组 |
| tick | 游戏的心跳，20 tick = 1 秒；tick 时间超 50 ms 就会卡 |
| Mixin | Fabric 生态里"在指定位置插一段自己的代码"的标准做法 |
| 插桩（Instrumentation） | 现在项目用的老办法，在类加载时改官方 jar 的字节码；脆弱且难维护 |
| 射线检测（raycast） | 从枪口沿视线方向做一次几何求交，判断打中了谁/什么 |
| SavedData / 数据附件 | 能存进存档的结构化数据，替代记分板当"状态仓库" |
| 资源包 | 只换贴图/模型/声音，不改逻辑；服务器可以下发给原版客户端 |

### 11.1 附：部署物扣账修复（2026-09-25，对应变更记录 v0.12）

作者反馈："部署成功退还一个（相当于没有消耗），部署失败退还两个（相当于多了一个）。"
排查与修复如下（都有实测支撑）：

- **生存模式本来就是对的**：吃下部署物（`minecraft:consumable`）→ 原版进度
  `pvpshot:use_cannon` 触发数据包部署 → 成功时净 **-1 件**，失败时数据包退还一件、净 **0 件**。
  用假人 `gamemode survival` + `player <假人> use continuous` 实测确认：成功一次 → 部署物 -1，
  结构正常出现；失败一次（在大厅保护区里）→ 部署物数量不变、聊天栏出现失败提示。
- **根因在创造模式**：原版 `Consumable#onConsume` 的顺序是"先触发 `consume_item` 进度
  （数据包据此部署/退还）→ 再 `ItemStack#consume(1, user)` 扣物品"，而
  **`ItemStack#consume` 对"无限材料"玩家（创造模式）不扣**。于是创造模式里：
  部署成功 = 一件没少（看起来像退还），部署失败 = 净多一件 —— 正是作者看到的现象。
- **修复**：模组新增部署物扣账观测 `pvpshot.weapon.DeployRefundWatch`。它把部署物自带的
  `minecraft:use_cooldown` 冷却"从没有变成有"当作"刚完成一次部署"的信号，
  **只在创造模式下补扣一件**，使两种模式的账目一致（成功 -1、失败 0）；
  顺带把每次"消耗 / 退还"写进服务器日志（玩家名、游戏模式、坐标、数量变化），
  以后再出现对不上可以直接查日志定位。生存模式的行为完全不变。

### 11.2 团队死斗的两处修正（2026-09-25）

作者反馈："团队死斗里定位条显示的还是 A~E，团队死斗应该显示玩家" +
"死斗模式的重生点有概率落在 A~E 点位上，死斗应该始终用固定重生点"。两处都已修好：

1. **定位条（模组侧）**：校园数据包用 `#preset` 记模式 —— `0 = 团队死斗`、`3 = 三点`、`5 = 五点`；
   模组此前把 `0` 当成"还没设置"而回退到五点占领，于是死斗下 A~E 全都还亮着。
   现在 `0`（以及历史值 `1`）都识别为死斗：所有点位不发光、不给定位条广播，
   定位条只显示玩家。实测：死斗下 `waypoint list` 只有玩家，切回五点则 5 个点位 + 玩家。
2. **重生点（数据包侧）**：校园包 `ustc_pvp:respawn/red|blue` 里原本有一组
   "死斗用固定前线点"的规则（红队 A/E、蓝队 C/D），而 A~E 正是抢点点位所在地。
   删掉这两行后，死斗模式没有前线候选，直接走原有的兜底 —— **始终在红/蓝基地的固定重生点**
   （每队 3 个点随机一个）。抢点模式（`#mode=1`）"占点附近复活"的规则完全不变。
   实测：死斗重生落在 (-2109.5, 2, -1487~-1491)（红基地）；把 A 点设为红方占领、切回抢点模式，
   重生又回到 A 点的前线重生点 (-1989.5, 28, -1527.5)。

数据包改动按 `tools/datapack-patches/`（含说明与覆盖命令）留档，因为它改的是
`server/world/` 里的存档内数据包，而存档目录按规则不入库。
